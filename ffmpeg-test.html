These are the exact two transcode paths the main app uses — audio-only is the fast/lossless path for a file whose video already plays fine but whose audio codec doesn't (e.g. AC3); full transcode re-encodes everything and is the fallback when the video/container itself isn't playable.

Input filesystem

WORKERFS gives FFmpeg on-demand read access to the file straight from the browser's own Blob storage, without duplicating it into JS/WASM memory first — the app switched to this to avoid out-of-memory crashes on large files. MEMFS is the simpler, older approach (fetchFile() into a JS ArrayBuffer, then writeFile() into FFmpeg's virtual filesystem) — needs roughly 2x the file size in memory just to stage the input, but has less per-read overhead once staged, which can matter for I/O-heavy operations like a -c:v copy remux. Ignored for "Check playability only" (that op never touches FFmpeg at all).

Streams the result straight to a file you choose, in bounded chunks, instead of holding the whole thing in browser memory at once — matters for large files. Requires a browser with the File System Access API.
